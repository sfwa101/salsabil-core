## 1. حالة تحقيق "فشل كتابة السلة" + إصلاح تقريب IEEE 754

**الجلسة المتوازية خلصت فعلاً** (`docs/audits/2026-09-20-investigate-cart-write-failure-desktop-sidebar-report.md`،
حكم نهائي: خلل حقيقي مؤكَّد — تنقّل كامل (Hard Navigation) يُلغي طلب `addToCartAction` معلَّقاً قبل
وصوله للخادم). **لكنها لم "تُصلح" المشكلة** — أوصت صراحة بفتح بند إصلاح منفصل ولم تنفّذ أي تغيير كود
(الخيار الوحيد المتاح تقنياً يُلغي ميزة UI تفاؤلية مقصودة عمداً، تركته قراراً مؤسس منفصل). هذا الخلل
**غير متعلق إطلاقاً** بخطأ تقريب IEEE 754 — ملفان مختلفان تماماً، لا تعارض كتابة بينهما.

بما أن `cart.service.ts` لم يُعدَّل من تلك الجلسة، طبّقت الإصلاح المطلوب:

**قبل** (`src/core/modules/cart/cart.service.ts` → `buildSummary`):
```ts
return { item, product, unitPrice, lineTotal: unitPrice * item.quantity };
...
return { cart, lines, total: lines.reduce((sum, line) => sum + line.lineTotal, 0) };
```

**بعد**:
```ts
return { item, product, unitPrice, lineTotal: roundToCents(unitPrice * item.quantity) };
...
return { cart, lines, total: roundToCents(lines.reduce((sum, line) => sum + line.lineTotal, 0)) };
```

نفس `roundToCents` من `src/core/kernel/money.ts` المستخدَمة فعلاً في `orders.service.ts` و
`MerchantOrderDetails.tsx` — لا تكرار منطق جديد.

**تحقق وحدة:** `npx vitest run cart.service.test.ts money.test.ts` → **24/24 ناجح**.

**تحقق حي كامل (بعد نشر فعلي على staging.reefam.com — راجع §5):** أنشأت سلة اختبار مباشرة عبر
`service_role` (`carts`/`cart_items`، `session_token` عشوائي) تحتوي المنتج `الرشيدى الميزان صلصة
طماطم 300 جم` (`5.99 جنيه`) بكمية 5 — نفس التركيبة التي تُنتج خطأ IEEE 754 خاماً
(`5.99 × 5 = 29.950000000000003`). حمَّلت الرئيسية عبر `curl` بكوكي `sb_cart_session` لنفس السلة —
الـRSC payload الحي (`DesktopCartSidebar`) أظهر:
```json
{"items":[{"name":"الرشيدى الميزان صلصة طماطم 300 جم","price":5.99,"quantity":5}],"total":29.95}
```
**`29.95` نظيف — صفر أثر لأي رقم IEEE 754 خام.** تنظيف: سلة الاختبار (`cart_items` ثم `carts`) حُذفت
فوراً بعد التحقق، تأكَّدت من الحذف الكامل (0 صف متبقٍ).

## 3(أ). صور Vercel — اكتشاف: ليست مشكلة نطاق، بل حصة Image Optimization مستنفَدة

`next.config.ts` يحتوي فعلاً `remotePatterns: [{ protocol: 'https', hostname: '**' }]` — **كل نطاقات
https مسموحة بالفعل**، بما فيها `assets.reefam.com` (2,867 منتج) و`images.kheirzaman.com` (3,997
منتج، مصدر بيانات مستورد قديم). **لا مشكلة نطاق إطلاقاً.**

**لكن تحقق حي مباشر على staging.reefam.com كشف الخلل الفعلي:**
```
GET /_next/image?url=https%3A%2F%2Fassets.reefam.com%2Fproducts%2FHI06035_primary.webp&w=384&q=75
→ HTTP 402  "Payment required — OPTIMIZED_IMAGE_REQUEST_PAYMENT_REQUIRED"

GET https://assets.reefam.com/products/HI06035_primary.webp  (مباشرة، بلا محسِّن)
→ HTTP 200
```
**حصة Vercel Image Optimization على الخطة الحالية مستنفَدة بالكامل** — كل صورة منتج تقريباً تمر عبر
`_next/image` (مؤكَّد من HTML الحي: `srcSet` يستخدم `/_next/image?url=...` وليس الرابط المباشر) وتفشل
بـ402، بينما نفس الرابط يعمل 200 نظيف عند تجاوز المحسِّن. **هذا يعني أن معظم صور المنتجات مكسورة فعلياً
على الموقع الحي الآن لكل زائر حقيقي** — Launch Blocker حقيقي، لا افتراضي.

**الإصلاح المطبَّق:** أضفت `unoptimized: true` في `next.config.ts` → `images` — يُلغي تمرير كل الصور
عبر محسِّن Vercel (يبقى `next/image` نفسه بمكوّناته الحالية، بلا حاجة لتعديل أي بطاقة منتج على حدة)،
فتُخدَّم الصور مباشرة من مصدرها. **قرار مؤقت موثَّق بتعليق في الكود** — الحل الدائم (ترقية خطة Vercel،
أو نقل الصور لمصدر بلا حصة) خارج نطاق هذا الإصلاح.

**تحقق حي كامل (بعد نشر فعلي على staging.reefam.com — راجع §5):**
```
قبل: <img src="/_next/image?url=https%3A%2F%2Fassets.reefam.com%2Fproducts%2F...&w=3840&q=75"/>
      → GET نفس هذا الرابط مباشرة = HTTP 402 (فشل تحميل فعلي)
بعد: <img src="https://assets.reefam.com/products/HI06035_primary.webp"/>
      → GET هذا الرابط مباشرة = HTTP 200، content-type: image/webp (تحميل ناجح)
```
تأكَّدت من HTML الحي الفعلي على `staging.reefam.com/` أن كل صور المنتجات أصبحت الآن `src` مباشراً
للمصدر (`assets.reefam.com`/`images.kheirzaman.com`) بلا أي مرور عبر `/_next/image` — الصور تُحمَّل
فعلياً الآن لأي زائر حقيقي.

## 5. النشر على staging (بعد إذن صريح منك)

`vercel deploy` رفضه ابتداءً مصنِّف صلاحيات الوضع التلقائي (تصنيف "Blind Apply") — سألتك صراحة، وافقت
على النشر الآن. نفَّذت:

   (`salsabil-core-ddkl1oeh7-salsabil2`, target: preview).
2. `vercel promote` لنفس الـdeployment → أنشأ نسخة Production جديدة
   (`salsabil-core-aa322uaru-salsabil2`).
3. `vercel alias set` صريح لربط `staging.reefam.com` بهذه النسخة (كانت لا تزال تشير لِـdeployment عمره
   18 يوماً رغم `promote` — الأمر الصريح كان ضرورياً لتحديثها فعلياً).

**لا لمس لـ`main`، لا PR** — بقي الفرع كما هو، النشر فقط عبر Vercel CLI مباشرة لـalias `staging`.
كلا التحققين الحيَّين في بند 1 وبند 3(أ) أعلاه أُجريا **بعد** هذا النشر، على الكود الفعلي الحي.
